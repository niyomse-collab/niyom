# v2: ภาพใหญ่สำหรับงานร้านป้าย

ปรับตามคำขอวันที่ 12 ตุลาคม 2569: ขนาด 700 × 40 ซม. ที่ 300 DPI เป็นเพียงตัวอย่าง โปรแกรม v2 ต้องรักษาจำนวนพิกเซลปลายทางตามขนาด/อัตราขยายและ DPI ที่ผู้ใช้ป้อน

## พฤติกรรมที่เปลี่ยน

- v2 เลิกใช้เพดานด้านภาพ 120,000 px และจำนวนพิกเซลรวม 450 ล้าน px เดิม
- ช่องอัตราขยายพิมพ์จำนวนเต็มบวกเองได้ เช่น 16x หรือ 32x เมื่อใช้ขนาดพิมพ์ โปรแกรมคำนวณพิกเซลจากขนาดและ DPI ที่ป้อน
- งานใหญ่เปลี่ยนวิธีประมวลผลเป็นส่วนและใช้ไฟล์ TIFF/BigTIFF ระหว่างทำงานบนดิสก์ โดยรักษาขนาดปลายทางเดิม
- นำเข้าภาพใหญ่และสร้าง Preview/1:1 โดยอ่านเฉพาะบริเวณที่แสดงบนหน้าจอ ภาพตัวอย่างย่อไม่มีผลต่อขนาดไฟล์จริง
- อัตราขยาย AI เดิม 2x, 4x และ 8x ยังใช้ weights และ FP32 เดิม ส่วน 8x ใช้ 4x ตามด้วย 2x ขนาดปลายทางที่มากกว่านี้ใช้การปรับขนาดหลัง AI; จำนวนพิกเซลที่เพิ่มขึ้นไม่ใช่การรับรองรายละเอียดใหม่จากต้นฉบับ
- เปิดล็อกสัดส่วนใช้ Fit และพื้นที่ขาวตามเดิม ปลดล็อกใช้ Stretch เต็มขนาดที่ป้อน
- PNG/RGB บันทึกแบบ lossless; TIFF เปลี่ยนเป็น BigTIFF อัตโนมัติเมื่อจำเป็น; PDF ใช้ส่วนภาพแบบ lossless บนหน้าเดียวและรักษาขนาดจริงด้วย UserUnit
- CMYK/ICC แปลงเฉพาะตอนส่งออก ใบหน้าที่เลือกใช้การประมวลผลเฉพาะบริเวณในงานใหญ่
- กดยกเลิกหรือเกิดข้อผิดพลาดจะล้างไฟล์ระหว่างทำงาน ไฟล์ปลายทางเดิมถูกแทนที่หลังงานสำเร็จเท่านั้น

## ทรัพยากรและรูปแบบไฟล์

พื้นที่ว่างบนดิสก์เป็นทรัพยากรหลักของงานใหญ่ TIFF ระหว่างทำงานเก็บ RGB 8 bit แบบไม่บีบอัดประมาณ 3 ไบต์ต่อพิกเซล บวกส่วนขอบของ tile และ metadata ถ้าใช้ AI จะมีต้นฉบับและผลระหว่าง pass อยู่พร้อมกัน โปรแกรมแจ้งเมื่อพื้นที่ไม่พอและรักษาค่าขนาดงานเดิม

งานเล็กคงเส้นทางประมวลผลเดิม งานที่เกินเกณฑ์หน่วยความจำเปลี่ยนไปใช้เส้นทางดิสก์ เกณฑ์นี้เป็นการเลือกวิธีทำงาน ไม่ใช่เพดานรับงาน

JPG มีข้อจำกัดด้านภาพ 65,500 px จาก encoder จึงต้องเลือก PNG, TIFF หรือ PDF เมื่อต้องการด้านภาพยาวกว่านั้น โปรแกรมแจ้งรูปแบบที่เหมาะสมโดยไม่ลดจำนวนพิกเซลหรือ DPI ส่วนขนาดที่เกินช่วงตัวเลขของ libvips/รูปแบบ PDF จะแจ้งข้อจำกัดจริงของรูปแบบ

## ผลทดสอบในสภาพแวดล้อมพัฒนา

| กรณี | ผล |
|---|---|
| ป้าย 700 × 100 ซม., 300 DPI, Stretch, PNG, ไม่ใช้ AI | สร้างไฟล์จริง 82,677 × 11,811 px สำเร็จ เกินเพดาน 450 ล้าน px เดิม |
| ไฟล์ PNG ด้านกว้าง 130,001 px | สร้างไฟล์จริงสำเร็จ เกินเพดานด้านภาพเดิม |
| PNG ต้นฉบับ 20,000 × 10,000 px | นำเข้าและบันทึกที่ขนาดเดิม 200 ล้าน px สำเร็จ |
| PNG/TIFF/JPG/PDF | ตรวจขนาด, DPI/ขนาดจริง, สีตรงกลาง และ Fit/Stretch |
| AI แบบแบ่งส่วน | ตรวจ pass 2x/4x/8x, เป้าหมาย 16x, ขนาดส่วนภาพ, context และรอยต่อด้วย backend ทดสอบ |
| AI จริงบน CPU, PyTorch 2.11.0+cpu, weights RealESRGAN_x4plus ที่ตรวจ SHA-256 แล้ว | ภาพทดสอบ 17 × 13 px ผ่าน 4x/8x และเป้าหมาย 16x; ผล 4x แบบแบ่งส่วนตรงกับเส้นทางเดิมแบบ tile ทุกพิกเซลบนตัวอย่างนี้ |
| หยุดงาน, inference ผิดพลาด, พื้นที่ดิสก์ไม่พอ | ไฟล์เดิมคงอยู่และไม่มีไฟล์งานค้าง |
| BigTIFF และ PDF หลายส่วน | เปิดอ่านได้และต่อพิกเซลครบตามต้นฉบับทดสอบ |
| Preview และ Protect | แสดงเฉพาะ viewport และรักษารายละเอียดต้นฉบับเฉพาะใบหน้าที่เลือก |

การทดสอบต้นฉบับ 200 ล้าน px หลังเปลี่ยน TIFF ระหว่างงานใช้ peak RSS ประมาณ 164 MB บน Linux ส่วนการสร้างป้าย 700 × 100 ซม. ใช้ต้นฉบับสีเรียบขนาดเล็ก ใช้เวลาประมาณ 18 วินาทีและ peak RSS ประมาณ 136 MB การวัดนี้เป็นการทดสอบ I/O/resize/export โดยไม่โหลด UI/PyTorch/โมเดล ภาพจริงและเครื่องอื่นอาจใช้เวลา/หน่วยความจำต่างกัน

ชุดทดสอบในเครื่องพัฒนาผ่าน 141 รายการ รวมการทดสอบ native SR ที่ใช้ PyTorch การตรวจใน CI ที่ไม่ได้ติดตั้ง PyTorch จะข้ามชุด native SR ตามเดิมและยังตรวจงานภาพใหญ่ครบ

ยังต้องตรวจคุณภาพภาพร้านและ CUDA/DirectML บนเครื่องใช้งานจริง เส้นทางงานใหญ่คง weights/ความแม่นยำ FP32 และ context padding เดิม แต่ยังไม่ได้รับรองว่า GPU ทุกเครื่องให้พิกเซลเหมือนเส้นทางเดิมทุกจุด

## ติดตั้งส่วนเสริมสำหรับ v2

```bash
python -m pip install -r requirements_v2_large_images.txt
```

ชุด Windows spec เก็บ native extension/DLL และ license ของ libvips ไว้ด้วย Import smoke test เรียกใช้ libvips จริงเพื่อจับกรณีแพ็ก runtime ไม่ครบ

อ้างอิง API: [pyvips](https://libvips.github.io/pyvips/), [libvips](https://github.com/libvips/libvips), [tifffile](https://github.com/cgohlke/tifffile), [Real-ESRGAN](https://github.com/xinntao/Real-ESRGAN)
